# Claude Code model and Remote Control setup

This setup uses Opus 5.5 at medium effort for the main session's planning, integration, and difficult implementation. Following the user's preference to use available Claude capacity, normal divisible tasks are split with Codex by default (see below); keep tiny or indivisible work local. When a bounded native edit or test run benefits from parallel work, the optional Sonnet 5 implementation worker receives explicit file ownership and acceptance criteria. Use a single high-effort Opus code or security review for material risky changes. Keep Fable advisor/verifier available only on explicit request. This is a token-aware baseline, not a measured global minimum; actual cost and speed depend on the task and account.

Use focused reads and deterministic tools, a short plan for complex work, concise worker evidence, and relevant acceptance checks. Stop when those checks pass; rerun broad checks only after a change, failure, or a specific unresolved risk. Reassess after two identical failed approaches. Avoid automatic model switching, extra review passes on small changes, and autonomous agent-loop services. The idle Remote Control host is a separate server process that keeps the Mac reachable; it does not run agent tasks by itself.

## Cross-harness collaboration

Following the user's preference to use available Claude capacity, normal actionable tasks that admit a useful division use the shared `cross-harness-collab` skill by default: assign at least one bounded subtask to the other harness while the owner advances an independent part. Do not wait for ambiguity, failures, or risky review; keep only tiny or indivisible tasks and simple answers local. This supersedes the earlier advice-only rule. The main session owns planning, integration, and the final decision; within Codex, Luna executes and Astra judges, and Claude execution defaults to Opus 5.5 medium. Default to one external worker with explicit disjoint owned paths and acceptance checks; do not duplicate work. Task authorization covers bounded local edits and tests, not unrelated external side effects. If the route is unavailable, report that and continue native work without claiming the other harness participated. Existing sessions may retain already-loaded instructions; start a new session to reliably load policy updates.

The helper takes a compact brief on stdin and returns a structured JSON receipt:

```sh
printf '%s\n' 'Goal: ...' 'Acceptance: ...' | \
  python3 ~/.agents/skills/cross-harness-collab/scripts/consult.py \
  --target codex --cwd "$PWD" --mode work --owned-path src/foo.py
```

- `--mode work` edits assigned files and runs scoped tests. It requires one or more `--owned-path` values (relative to `--cwd`) and defaults to Codex `gpt-6-luna` high in a `workspace-write` sandbox, or Claude `claude-opus-5-5` medium with Read/Glob/Grep/Edit/Write/Bash under `acceptEdits` and a $5 budget; timeout 600 s.
- `--mode consult` (default, backward compatible) is read-only: Codex `gpt-6-astra` low in a `read-only` sandbox, or Claude `claude-opus-5-5` medium with Read/Glob/Grep and a $1 budget; timeout 120 s. Allow one pass and at most one focused follow-up, then decide. That bound applies to discussion, not work: the owner may issue further distinct scoped tasks or revisions.

Explicit `--model`/`--effort` choices win; there is no silent fallback. Owned paths are an instruction-level coordination contract, not an OS per-file sandbox: the helper checks they stay inside `--cwd` but does not enforce which files the worker edits, so the owner inspects changes, integrates, and verifies. A work receipt with `status: "returned"` and `task_verified: false` records only the agent's response; the owner must inspect artifacts and run acceptance checks. Preflight errors set `partial_changes_possible: false`, while failures after launch set it true; inspect before retrying. Worker- and peer-marked briefs (`CROSS_HARNESS_WORKER=1` / `CROSS_HARNESS_PEER=1`) must not spawn peers or native agents, and the helper refuses nested calls. Set any outer-runner timeout about 15 seconds above `--timeout`; `SIGKILL` on the helper cannot be intercepted. `model_verified: false` means serving identity is unverified.

This is an on-demand CLI call; it does not require a background service or hook. The helper keeps Codex's installed auth while ignoring user config, execpolicy rules, and hooks; it runs ephemeral, with `project_doc_max_bytes=0`. Include relevant repo rules in the brief because this route intentionally omits project instructions. Claude's route uses the installed CLI's auth, safe mode, empty setting sources, no MCP servers, and no session persistence. For Codex, the helper resolves symlinks to the real CLI executable and prepends its bundle directory to the child `PATH`; this is invocation-scoped. Historical note from the earlier consult-only design: the measured Codex smoke correctly found the sign bug, but the comparison run also enabled experimental `skip_host_skill_discovery`; input changed by only about 1% (23,715 to 23,477 tokens across separate runs), so that experimental flag was removed without evidence of meaningful savings.

The public settings template selects Opus 5.5 and saves medium effort per model; it also saves medium for Sonnet 5. The optional worker's own frontmatter selects Sonnet 5 at medium effort. The template disables prompt suggestions and keeps `remoteControlAtStartup` enabled. It is a comprehensive portable recovery snapshot, not a recommendation to activate every listed plugin or hook. Live settings were updated narrowly; do not replace them wholesale from the template.

## Keeping the Mac reachable

The Desktop **Connect new sessions to Remote Control** preference and `remoteControlAtStartup` control how new Claude sessions connect; neither keeps a Remote Control host process running on its own. iOS Remote needs the Mac's Remote Control server to be active. The verified login-scoped LaunchAgent is `/Users/gotasasaki/Library/LaunchAgents/local.claude.remote-control.plist`; it starts `/Users/gotasasaki/.local/bin/claude remote-control --name "Mac agents-setup" --spawn=worktree --capacity 4` at login and keeps it running. It requires the Mac user to remain logged in and the Mac to have network access.

Check it with `launchctl print "gui/$(id -u)/local.claude.remote-control"`. The service's stdout and stderr are `/Users/gotasasaki/.claude/remote-control/stdout.log` and `/Users/gotasasaki/.claude/remote-control/stderr.log`. The service was verified running on this Mac and visible in Claude Desktop under **Code > Local > Remote Control**; iOS availability still awaits user confirmation.

To stop the login-scoped host, run `launchctl bootout "gui/$(id -u)/local.claude.remote-control"`; this ends Remote Control availability until the service is loaded again.

Anthropic's [model configuration guide](https://code.claude.com/docs/en/model-config) describes model IDs and effort levels; [subagents](https://code.claude.com/docs/en/sub-agents) describes agent model and effort settings; [settings](https://code.claude.com/docs/en/settings) documents `modelSettings`, `promptSuggestionEnabled`, and `remoteControlAtStartup`; [Remote Control](https://code.claude.com/docs/en/remote-control) describes remote sessions.

# Vantik question highlights

## 適用範囲

全試験・全問題・全選択肢を対象とする共通工程。過去問・オリジナル、既存問題・新規取込、単一選択・複数選択、各提供言語を含む。SAP限定、過去問限定、未合格試験限定の条件を共通ルールへ持ち込まない。個別依頼が対象を限定している場合はその範囲で実行し、残りまで更新済みとは報告しない。

問題の取得・取込・作成・解説変更では、この工程を完了条件に含める。単なる取得だけの依頼を本番取込の許可とは扱わない。

## 強調する内容

### 問題ごとの判定（2026-11-08の指定）

先に設問全体を次のいずれかに分類し、理由を記録する。全問題を確認対象とするが、すべての選択肢に必ず強調を付けるという意味ではない。

- **通常の判定問題**: 正解だと判定できる最短の十分なフレーズに正解ハイライト、不正解だと判定できる最短の十分なフレーズに不正解ハイライトを引く。
- **消去法で解く問題**: 正解を積極的に確定する語句がなく、不正解の除外によって答えを選ぶもの。不正解ハイライトのみとし、残った正解へ正解ハイライトを付けない。単に消去法も使えるというだけで、通常の問題をこの分類にしない。
- **単語・名称を答える問題**: この選択肢強調の対象外。選択肢がサービス名や用語名だけなど、語を答える設問かを意味で判定する。保存済みの `strategy` や正答キー・出典事実の確信度より、この分類を優先する。出典の不足で正答キーが曖昧でも、サービス名だけを答える問題を選択肢強調の保留にせず、事実上の疑義は別の審査記録に残す。短さだけでコード・設定・条件比較の問題まで除外しない。設定内容・設定値・条件・操作と対象の関係を問う混合問題も、選択肢に名称があるだけで対象外にしない。

最短とは、さらに削ると正誤の判定根拠が失われる長さ。文全体を既定にせず、否定、値、範囲、動作と対象の関係など必要な条件は残す。対象外の問題と、消去法の正解側の非表示は正常な結果として数え、未処理や理由不明の保留と区別する。保留を理由に古い強調を残さない。

- **正答条件 (`correct_reason`)**: 正解を成立させる要求・制約・設定・組合せの決め手。補完する複数の語句が必要なら組み合わせる。
- **除外理由 (`elimination_reason`)**: 不正解を外せる具体的な条件違反・設定の誤り・比較上の不利。LEAST cost/effort/overheadでは、実現可能でも劣る理由を示し、不可能と断定しない。
- 問題文・全選択肢・正答集合・解説を照合し、短い因果の注記を付ける。サービス名だけで済ませず、判断を変える動作・対象・向き・範囲・否定・数値を残す。ただしAPI名やJSONキー自体が決め手なら、その完全な識別子を使える。
- 本文に実在する連続した語句を選ぶ。語の補完、翻訳による置換、途中の語の省略、識別子の切断をしない。言語ごとに同じ条件を指す語句を選び、その言語の本文に照合する。
- 設問にない要件や理想的な構成を追加せず、提示された選択肢の中で判定する。正答キーに合わせるために誤った除外理由を作らない。

## スロット形式の問題（Hotspot・ドラッグ&ドロップ・マッチング・並べ替え・dropdown・Yes/No）

原典がボックス・空欄・ステップ・記述ごとに1つずつ選ばせる問題は、取込元を問わずスロット形式の1問として扱う。

- **検知**: ExamCademy の `question_type` が `dropdown`（ユースケースごとの選択、ステップの並べ替え）または `statements`（記述ごとの Yes/No）。ExamTopics などで設問冒頭が `HOTSPOT -`・`DRAG DROP -`・マッチング・並べ替えのもの。既存データでは選択肢ラベルが `S<ボックス番号>-<文字>` のもの。
- **保存形式**: 1問の中に全ボックスを持つ。ラベルは `S1-A`, `S1-B`, `S2-A`…、本文は `[<ボックス見出し>] <選択肢>`（既存の `<見出し>: <選択肢>` も可）。正解はボックスごとにちょうど1つ。同じボックスの選択肢は全言語で同じ見出しを共有し、翻訳でも `[見出しの訳] 選択肢の訳` の形を保つ。Yes/No は `はい`／`いいえ` とする。Vantik はこの形式をボックスごとのグループとして表示し、ボックス内で1つだけ選ばせる。
- **禁止**: ボックス・空欄・記述ごとに別問題へ分解しない。2〜3択の単問になり、本試験の形式と難度を失う（2026-11-15 に MLA-C01・SCS-C03・CCAR-P で発生し、`merge_slot_questions.cjs` で1問に戻した）。「正しい記述をすべて選択」の複数選択へ置き換えない。変換できない形式は分解せず、具体的な理由付きで保留する。
- **ハイライト**: 表示時は見出しが選択肢本文から外れてボックスの見出しになる。選択肢キーポイントは見出しではなく選択肢本文側の語句から選び、正答条件・除外理由はそのボックスの見出しに対して判定する。設問全体の条件は設問本文側のハイライトに置く。
- **確認**: 取込では、ボックスごとに正解1つ、見出しの共有（英日とも）、ボックス数を検査する。実画面では、ボックスごとのグループ表示、ボックス内での選び直し、全ボックスを選ぶまで回答できないこと、採点後のボックス単位の正誤と理由表示を、モバイルで確認する。

## データと表示

1. 正答・不正解は保存された正答集合と安定した `choice_id` から決める。シャッフル後の表示ラベルを識別子にしない。設問の条件ハイライトとは区別する。
2. 正答条件は緑の実線、除外理由は赤の波線など、色と線種で区別し、凡例を付ける。回答前と成績非表示時には、正答を示す強調・注記・凡例を隠す。回答後は選んだ選択肢に限らず、問題分類に応じて対象となる選択肢に表示する。消去法の正解側と単語回答問題にはこの強調を出さない。
3. 通常演習、問題バンク、回答振り返り、リハーサル履歴、機内モードの各経路で同じ意味を保つ。履歴が固定する旧版はその版の本文・正答・choice IDに独立に照合し、現行版のIDを転用しない。
4. 現行実装の適用条件を確認する。試験コード、過去問分類、特定source名に依存する一回限りの実装・適用ツールを、全問題対応とみなして流用しない。全問題へ適用する際は型・API・表示・保存データの経路も対象範囲に対応させる。

## 論点・サブ論点の付与（2026-11-28の指定）

未合格の試験（`learning_settings` の `archived_exam_codes` にない試験）へ問題を取り込む・作成するときは、新しい問題すべてに論点とサブ論点を付けるまでを完了条件に含める。論点は公式のタスク区分（番号付き。AWSなら `1.1` など）、サブ論点はその試験が問う具体的な判断ポイント1つ。タグの正本は reskilling-os の `server/data/content/topic_tags/<EXAM>.json`（論点カタログ）で、サーバー起動時に本番へ自動反映される。手順の詳細は reskilling-os の `docs/topic-tags.md`「Tag newly imported questions」。

1. 取込後、論点が付いていない問題を書き出す。本番に取り込んだ場合は `ssh ugnas docker exec vantik vantik export-topic-tag-tasks --exam-code <EXAM> --untagged --out /app/data/topic-tasks.jsonl` の後に `ssh ugnas docker exec vantik cat /app/data/topic-tasks.jsonl > topic-tasks.jsonl` で手元に取る。本番がまだ論点カタログ対応前の版なら、オンラインバックアップのコピーに対して `node --import tsx server/cli/main.ts export-topic-tag-tasks --db <copy> …` を使う。
2. カタログに載っている論点・サブ論点だけを使い、問い（問題文末尾）と正解の選択肢から1問1タグで分類する。2つの判断を同時に問う問題だけ2タグにする。どのサブ論点にも合わない問題が同じ判断ポイントで2問以上あるときだけ、新しいサブ論点を taxonomy ファイル（`{"topics": [{"name": "<論点>", "subtopics": ["<サブ論点>"]}], "sources": [...]}`）で足す。名前は日本語40字以内、`>` と改行を含めない。カタログのない試験は、公式試験ガイドのタスク区分から論点を作り、実際の問題を読んでサブ論点を1つあたり8〜15問を目安に作る。AWS試験は `server/data/content/flashcards/<EXAM>.json` の `task` 番号と論点番号を照合する。大量の分類は Haiku で足りる（2026-11-28 の試行で盲検判定 95% 妥当、Sonnet 88%）。
3. 1行1問 `{"k": "<stable_key>", "tags": ["<論点> > <サブ論点>"]}` を書き、`node --import tsx server/scripts/merge_topic_catalog.ts --catalog server/data/content/topic_tags/<EXAM>.json --assignments classified.jsonl [--taxonomy new-topics.json]` でカタログへ統合する。既に別のタグが付いたキーは `--replace` なしでは上書きされない。
4. `npx vitest run server/services/topicCatalog.test.ts` を通し、reskilling-os にコミットして PR を出す。デプロイ後の起動で本番に反映される。デプロイ済みで起動を待たずに反映したいときは `ssh ugnas docker exec vantik vantik apply-topic-catalog --exam-code <EXAM>` のドライランを確認してから `--apply` を付ける（本番DBへの書き込みなので、取込と同じ承認範囲・オンラインバックアップの後に行う）。
5. 完了の証拠: `export-topic-tag-tasks --untagged` が0件、`apply-topic-catalog --exam-code <EXAM>` のドライランで `missing_questions` 0・`applied` 0、付与した問題数とサブ論点の新設数を報告する。

## 欠落を残さない確認

- 対象の問題版と選択肢ID集合を先に固定し、全件を「審査済み・描画可能」または「具体的理由付き保留」に一意に対応させる。対象外・未処理・保留を混同しない。最終監査では `strategy=word_answer` だけに絞らず、曖昧・保留分類も設問と選択肢の意味から見直し、単語・名称問題の見落としを確認する。
- 一つの選択肢の疑義を問題全体へ波及させない。他の選択肢は独立に審査する。解説欠落も一律保留にせず、設問・選択肢・必要な公式根拠から判断できるか確認する。
- 候補の書き方の失敗（焦点ずれ、誤った注記、引用不一致、空出力）は修正対象。元データの矛盾・情報欠落とは区別する。「最後の候補が不適切」だけで残件確認を終えず、具体的な代替語句か、判断を妨げる根拠を示す。
- 不安定・不確かな仕様は現行の公式資料で確認する。生成と独立審査の記録を分け、本文・正答・候補・審査結果をホスト側のIDとハッシュで結ぶ。モデルにIDやハッシュを作らせない。
- 文字列一致だけで合格にしない。実際の用語正規化、選択肢整形、Markdown/React描画を通して両言語を確認する。メール・URLリンクやインラインコードをまたぐ語句、複数行JSONは描画できない場合がある。意味を保つ短い節や識別子に分け、再審査する。
- 大量の描画検査が停止する場合は、全件の順序とIDを保って小分けにし、各部分の行数・出力・全フレーズの結果を結合して検証する。部分成功を全件成功にしない。タイムアウトやSIGINT/SIGTERMでも、その検査が起動したプロセス群を停止・回収し、残存0を確認する。再実行は入力・審査・出力予定のハッシュを固定した新しい保存先で行い、CLIの実際の起動経路も検証する。

## 反映と完了の証拠

今回のルールに適合する既存の強調、設問本文、正答、解説、他の対象、学習履歴を保持する。対象問題の既存の選択肢強調も分類と最短根拠に照合し、対象外の問題・消去法の正解側に古い選択肢強調が残らないよう整理する。設問本文側の条件ハイライトは選択肢強調と区別して保持する。変更しない対象と現在の正しい行をID・値まで固定する。本番更新は既存の承認範囲を確認し、SQLiteオンラインバックアップ、コピーでの試行、短い保護トランザクション、整合性検査、再実行0変更で検証する。無関係な正答キーや本文を修正しない。
- 保留解除など承認済みの対象では、事実上の注意・保留記録と強調の保存状態を分ける。対象ID・sourceを固定した計画で未根拠の既存強調だけを明示的に消し、他の選択肢の強調と正答キーは維持する。反映後は注意対象のchoice IDごとに管理対象の選択肢キーポイント行が0件であることを確認する。保留の旧スナップショットとAPIが一致しても、保留分岐がDMLを省略して古い行を残す実装ならユーザー向け方針の合格証拠にはならない。無条件削除や対象外への波及はしない。

反映後は実際に配信されるAPIとモバイル実画面で、日英・ライト/ダーク、採点前非表示・採点後全択表示を確認する。保存済みの機内モードパックはスナップショットなので、同期・再取得の状態も別に確認する。

問題IDと問題版IDを混同せず、APIが受け付けるIDを実装で確認する。対象に非表示・無効化された出典の問題を含む場合、画面APIの404を未反映と即断しない。可視範囲はAPIと実画面、不可視範囲は読み取り専用DBで本文・翻訳本文・正答集合・強調を照合し、それぞれの件数を示す。検証のために表示設定を変更したり、不可視の対象を未処理数から黙って除外したりしない。

対象総数、強調済み数、保留数・具体的理由、未処理0、履歴保持、配信・表示検証を報告する。ローカル成功だけ、審査済みだが未反映の候補、SAPだけの更新を、全問題への反映完了と報告しない。

# Exam trap choices

Use this skill to identify a wrong choice that is plausible for a specific reason, yet loses to the keyed answer because of a material scenario condition or stated priority while remaining relatively plausible among the wrong choices. The goal is a reviewable candidate set, not a forced label for every question.

Read [references/patterns.md](references/patterns.md) for source-grounded semantic patterns and their limits. Read [references/vantik.md](references/vantik.md) only when the input comes from Vantik.

For each question:

1. Preserve the stable source question ID and version ID (or content hash), original choice indexes, and labels. The question ID identifies the question itself, not only its provider. First verify that the answer key is present and internally usable. Do not renumber options based on display order. If the key or an explicit source mapping conflicts with the choices and the conflict cannot be resolved, hold the question even when a source label is present.
2. Normalize what the question asks: positive or negative/EXCEPT polarity; single or multi-select; required number of selections; and any ranking such as first, best, minimum cost, or operational burden. Correct-answer membership is determined by the answer key for the normalized question, not by whether an option's standalone claim is true. For single-select combination answers, compare the atomic claims in each option; do not reject a choice merely because it combines claims. For multi-select questions, hold candidate labeling unless the selection rules support judging each choice independently.
3. Extract the scenario's explicit requirements, constraints, phase, scope, and priorities. Check whether the answer key satisfies them before judging distractors. If the key appears invalid or stale, hold the question for answer review.
4. Compare every wrong choice with the key and with the other wrong choices. Record each choice's plausible appeal, the decisive requirement or priority it misses, and why it is weaker, stronger, or tied relative to the competing distractors. Link the decisive gap to the specific stem requirement and answer-key basis. A technically valid choice can still lose on polarity, phase, scope, or a stated optimization priority; do not call it technically false without evidence.
5. Accept a source-designated label as `source_label` only when the explicit mapping is consistent with a usable answer key and the normalized question. Preserve any supplied existing flag too. If the existing flag conflicts with the source mapping or proposed choice, use `held` and leave the accepted trap empty until the conflict is reviewed. A source mapping takes precedence over a model's competing guess only when it does not collide with the existing flag or key. Otherwise, mark a model-inferred `candidate` only when one wrong choice has a clear, evidence-backed near-miss advantage over the others. If the comparison is complete but no wrong choice plausibly stands out, or several are tied, use `no_unique_trap`. If the answer basis is missing or conflicting, or a supplied source mapping is malformed or unsupported, use `held`. Absence of an explicit source mapping is normal for inference and does not by itself require holding the question. Do not invent a tie-breaker, force a minimal counterfactual, or meet a quota.
6. Compare choices by the material requirements and priorities stated in the question. Do not rank by counting shared components, surface resemblance, or unstated preferences. A `candidate` requires a resolved answer key, strong or moderate evidence, and no unresolved material uncertainty; if a tie or ranking uncertainty remains, use `no_unique_trap` when the comparison is complete and `held` when required evidence is missing or conflicting.
7. Keep provenance and decision separate: `source_mapping` preserves the original explicit label when supplied; `existing_flag` preserves an existing flag when supplied; `source_label` means the source mapping is accepted after key, polarity, and conflict checks; `candidate` means a model-inferred review candidate; `held` means evidence or conflicts need resolution; `no_unique_trap` means review found no plausible unique candidate. `trap_label` must exactly equal the selected choice's original label. Put taxonomy categories in the separate optional `pattern_id` field. Use qualitative evidence labels only, never calibrated probability.

Return structured JSON following the contract in [references/patterns.md](references/patterns.md). Include a stable question/version key and choice identifiers, original labels/indexes, source mapping, existing flag when supplied, evidence basis, decision, `trap_label` or null, normalized polarity and selection/ranking requirements, a rationale for the candidate's true appeal, its decisive gap, and its comparison with each competing distractor. For any inferred candidate, include the answer-key basis and resolve material uncertainty before labeling it. Keep explicit source mappings separate from inferred candidates and held questions. Run [scripts/validate_review.py](scripts/validate_review.py) on the review JSON; when available, also provide the normalized source question file with `--questions` to verify choice identities and conflicts.

This skill creates review output only. It does not authorize modifying an exam bank, database, or existing flags. Never overwrite a conflicting existing flag; surface the conflict for review. Before applying a reviewed result to a separate system, use that system's explicit workflow and authorization.
